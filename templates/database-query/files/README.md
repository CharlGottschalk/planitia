# {{name}}

An MCP server (stdio) that runs parameterized SQL against Postgres. Generated by planitia
from the `database-query` template in **{{mode}}** mode.

## Setup

```sh
npm install
npm run build
DATABASE_URL=postgres://user:password@localhost:5432/scratch npm test
```

The smoke test starts the server, lists its tools and runs queries. Its database tests need
`DATABASE_URL` to point at a **scratch database**: they create one `planitia_smoke_<pid>`
table and drop it again. Without `DATABASE_URL`, those tests are reported as skipped.

Set `DATABASE_URL` in the env of the MCP client entry (see below). The server reads real env
vars and does not load `.env`. `.env.example` lists the variable name only.

## Tools

### `query`

Runs one SQL statement. Values go in `params` and are referenced as `$1`, `$2`, ... in the SQL,
so they are never spliced into the SQL text.

| Input | Type | Description |
|-------|------|-------------|
| `sql` | string | One SQL statement, e.g. `SELECT * FROM public.orders WHERE id = $1` |
| `params` | array, optional | Values for `$1`, `$2`, ...: strings, numbers, booleans or `null` |

Returns `{ "rowCount": 1, "fields": ["id"], "rows": [{ "id": 1 }] }`. At most 1000 rows are
returned; a larger result is cut and marked `"truncated": true`. Postgres `bigint` and
`numeric` values come back as strings.

Annotations: read-only mode gives `readOnlyHint: true`, and read-write mode gives
`destructiveHint: true`.

`query` is generated only with `genericTools` set to `on` (this server: **{{genericTools}}**).
With `off`, the model can use only the tools below and any spec-defined tools.

### `list_tables`

Lists the tables and views the server's role can see, as `schema.table` names, leaving out
`pg_catalog` and `information_schema`. With a table allowlist, only allowlisted tables are listed.
Returns `{ "tables": ["public.orders", ...] }`. Read-only.

### `describe_table`

| Input | Type | Description |
|-------|------|-------------|
| `table` | string | `schema.table`, e.g. `public.orders` |

Returns `{ "table": "public.orders", "columns": [{ "name": "id", "type": "integer", "nullable": false }],
"primaryKey": ["id"] }`. With a table allowlist, other tables fail with `TABLE_NOT_ALLOWED`; a table
that doesn't exist (or that the role can't see) fails with `NOT_FOUND`. Read-only.

`list_tables` and `describe_table` read `information_schema` in a READ ONLY transaction, in either
mode. They apply the allowlist themselves rather than through `EXPLAIN`.

{{toolsReadme}}### Adding tools

Add a `sql` or `custom` tool with Planitia's `add-tool`, run in this directory:

```sh
npx github:CharlGottschalk/planitia add-tool --kind sql --name count_orders --description "Count orders" --readOnly true \
  --sql "SELECT count(*)::int AS n FROM public.orders"
npx github:CharlGottschalk/planitia add-tool --kind custom --name my_tool --description "..." --readOnly false --param id:integer
```

It adds the tool to `src/tools.json` (and, for `custom`, a handler stub in `src/tools/<name>.ts`
that returns `NOT_IMPLEMENTED` until you write it). It reads `planitia.json` and changes no other
file. Run `npm run build` afterwards. `add-tool --help` lists every option.

## Guardrails

- **Read-only by default:** in read-only mode each call runs inside `BEGIN TRANSACTION READ
  ONLY` and always ends with `ROLLBACK`. Postgres itself rejects INSERT, UPDATE, DELETE, DDL and
  `nextval()` (`READ_ONLY`). Nothing depends on inspecting the SQL text. Write mode is chosen at
  generation time (`--mode read-write`) and commits each call.
- **One statement per call:** queries use Postgres's extended protocol, which refuses more than
  one statement, so `SELECT 1; DELETE ...` fails as a whole.
- **Table allowlist** (`{{tables}}`; empty = off): when set, the query is first planned with
  `EXPLAIN` and every table in the plan must be on the list (`schema.table`, lowercase).
  Views count as the tables they read. Anything else fails with `TABLE_NOT_ALLOWED`. So do
  statements Postgres can't `EXPLAIN` (DDL, `TRUNCATE`, `COPY`), since they can't be checked.
  `DB_ALLOWED_TABLES` (comma-separated) replaces the list at runtime. It is set in the client
  entry's env, which the model calling the tool cannot change. Functions can read tables
  without them showing in the plan, so pair the allowlist with database permissions.
- **Use a least-privilege role:** connect as a role that can only reach what the tool should.
  The transaction mode and the allowlist limit what a query can do, but the role's own
  privileges are the real boundary.
- **Input validation:** every tool's inputs are checked with zod before it runs. Bad input
  returns an error result (`isError: true`), and the server keeps running.
- **Errors:** failures come back as error results with a code prefix: `READ_ONLY`,
  `TABLE_NOT_ALLOWED`, `NOT_FOUND`, `DB_ERROR` (with the Postgres error code), `CONFIG_ERROR`, `TIMEOUT`,
  `RATE_LIMITED` or `TOOL_ERROR`.
- **Logging:** JSON lines on stderr only. stdout carries the MCP protocol.
- **Timeout:** each call is limited to `TOOL_TIMEOUT_MS` (default {{timeoutMs}} ms). The same
  limit is set as Postgres's `statement_timeout`, so the database cancels the query too.
- **Rate limit:** at most `RATE_LIMIT_PER_MINUTE` calls per minute across all tools
  (default {{rateLimitPerMinute}}; 0 = off).
- **Cache:** `list_tables`, `describe_table` and, in read-only mode, every other tool's results are cached in memory for `CACHE_TTL_SECONDS`
  (default {{cacheTtlSeconds}}; 0 = off). Cached results can be stale.
- **Secrets:** the connection string is read from `DATABASE_URL`. It is never written to
  generated files; `.env.example` holds only the variable name.

## Configuration

| Env var | Default | Meaning |
|---------|---------|---------|
| `DATABASE_URL` | (unset) | Postgres connection string; required |
| `DB_ALLOWED_TABLES` | `{{tables}}` | Replaces the table allowlist, comma-separated `schema.table` |
| `TOOL_TIMEOUT_MS` | {{timeoutMs}} | Per-call timeout, also the Postgres statement timeout |
| `RATE_LIMIT_PER_MINUTE` | {{rateLimitPerMinute}} | Max calls per minute, 0 = off |
| `CACHE_TTL_SECONDS` | {{cacheTtlSeconds}} | Result cache lifetime (read-only mode), 0 = off |

## Register with an MCP client

Build first, then use the absolute path to `dist/src/index.js`.

**Claude Code**

```sh
claude mcp add {{name}} -e DATABASE_URL=postgres://user:password@host:5432/db -- node "$(pwd)/dist/src/index.js"
claude mcp list   # should show {{name}} as connected
```

Add `-e` for each other env var. `--scope project` shares the entry through `.mcp.json`, and the
connection string with it, so use it only if that file stays out of version control.

**Codex**

```sh
codex mcp add {{name}} --env DATABASE_URL=postgres://user:password@host:5432/db -- node "$(pwd)/dist/src/index.js"
```

Or add this to `~/.codex/config.toml`:

```toml
[mcp_servers.{{name|json}}]
command = "node"
args = ["/absolute/path/to/{{name}}/dist/src/index.js"]
env = { DATABASE_URL = "postgres://user:password@host:5432/db" }
```

**Cursor**

Add this to `.cursor/mcp.json` (project) or `~/.cursor/mcp.json` (global):

```json
{
  "mcpServers": {
    {{name|json}}: {
      "command": "node",
      "args": ["/absolute/path/to/{{name}}/dist/src/index.js"],
      "env": { "DATABASE_URL": "postgres://user:password@host:5432/db" }
    }
  }
}
```
